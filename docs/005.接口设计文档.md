#### 二、设计概述

**接口分层：**

| 层级 | 协议 | 消费方 | 说明 |
|------|------|--------|------|
| 外部接口 | RESTful API (HTTPS) | 客户端 → 云端服务器 | 数据的云端持久化与跨设备同步 |
| 实时通道 | WebSocket (WSS) | 客户端 ↔ 云端服务器 | 家庭数据变更的实时推送 |
| 内部接口 | C++ QObject 方法 | QML UI → Service 层 | UI 层调用业务逻辑的唯一入口 |
| 数据接口 | C++ 虚基类 | Service 层 → Repository 层 | 业务层与数据访问层的解耦契约 |

**通用约定：**

- **鉴权**：所有外部接口需在 Header 中携带 `Authorization: Bearer <token>`，WebSocket 连接时通过首条消息鉴权。
- **时间格式**：统一 ISO 8601（`2026-05-18T12:00:00Z`）。
- **分页**：列表接口统一使用 `?page=1&page_size=20` 参数，响应中包含 `total` 字段。
- **错误响应**：统一格式 `{ "code": "ERROR_CODE", "message": "描述", "details": {} }`。
- **ID 格式**：所有实体 ID 为 UUID v4 字符串。

**错误码体系：**

| 范围 | 含义 | 示例 |
|------|------|------|
| 1000-1999 | 认证与权限错误 | 1001=未登录, 1002=Token 过期, 1003=无权限, 1004=非当日掌勺人禁止核销 |
| 2000-2999 | 参数校验错误 | 2001=必填字段缺失, 2002=格式非法, 2003=值超出范围 |
| 3000-3999 | 业务逻辑错误 | 3001=邀请码无效, 3002=库存不足, 3003=食材被引用禁止删除 |
| 4000-4999 | 数据冲突错误 | 4001=版本冲突, 4002=唯一约束冲突 |
| 5000-5999 | 服务端错误 | 5001=内部错误, 5002=数据库异常 |

#### 三、RESTful API 接口定义

##### 3.1 用户与认证模块

---

**POST /api/v1/auth/register**

注册新用户，同时完成 TDEE 计算。

- **请求体：**
```json
{
  "login_id": "13800138000",
  "password": "plain_text_password",
  "nickname": "小明",
  "gender": 1,
  "height": 175.0,
  "weight": 70.0,
  "birth_date": "1995-06-15",
  "diet_goal": "weight_loss"
}
```

- **业务逻辑：**
  1. 校验 `login_id` 唯一性
  2. 使用 **Argon2id** 哈希 `password` → `password_hash`（安全设计文档 v1.0 推荐算法）
     - 参数：内存消耗 64MB，迭代次数 3，并行度 4
     - 格式：`$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>`
  3. 根据 `gender`、`height`、`weight`、`birth_date` 调用 Mifflin-St Jeor 公式计算 BMR 与 TDEE
  4. 自动创建 `taste_preferences`（默认 0.5）和 `nutrition_profiles`（默认比例）记录
  5. 返回 JWT Token（access_token + refresh_token）

- **Mifflin-St Jeor 公式：**
  - 男性：`BMR = 10 × weight(kg) + 6.25 × height(cm) - 5 × age - 161 + 166`（即 `10W + 6.25H - 5A + 5`）
  - 女性：`BMR = 10 × weight(kg) + 6.25 × height(cm) - 5 × age - 161`（即 `10W + 6.25H - 5A - 161`）
  - `TDEE = BMR × 活动系数`（默认 1.375 = 轻度活动）

- **响应体：**
```json
{
  "user": { "id": "uuid", "nickname": "小明", "bmr": 1680.0, "tdee": 2310.0 },
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "expires_at": "2026-05-18T12:15:00Z"
}
```

---

**POST /api/v1/auth/login**

- **请求体：** `{ "login_id": "13800138000", "password": "plain_text_password" }`
- **业务逻辑：** 校验 `login_id` + `password`，生成 JWT Token
  - **access_token**：短期令牌，有效期 **15 分钟**，用于 API 访问
  - **refresh_token**：长期令牌，有效期 **7 天**，用于刷新 access_token
  - Token Payload 包含：`user_id`, `family_id`, `role`, `jti`（唯一标识）
- **响应体：**
```json
{
  "user": { "id": "uuid", "nickname": "小明", ... },
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "expires_at": "2026-05-18T12:15:00Z"
}
```

---

**PUT /api/v1/users/{id}/profile**

更新用户个人档案，触发 TDEE 重算。

- **请求体：**
```json
{
  "nickname": "小明",
  "gender": 1,
  "height": 176.0,
  "weight": 68.5,
  "birth_date": "1995-06-15",
  "diet_goal": "muscle_gain",
  "avatar_url": "https://..."
}
```

- **业务逻辑：**
  1. 仅允许修改自己的档案（`{id}` 必须等于 Token 中的 user_id）
  2. 任何身体数据变更均触发 BMR/TDEE 重算
  3. 若 `diet_goal` 变更，同步更新 `nutrition_profiles` 的供能比默认值
  4. 携带 `version` 字段进行乐观锁校验

- **响应体：** `{ "user": { ... }, "version": 2 }`

**POST /api/v1/auth/refresh**

刷新 Token。请求体：`{ "token": "current_jwt" }`。响应体：新 Token。

##### 3.2 家庭管理模块

---

**POST /api/v1/families**

创建新家庭。

- **请求体：** `{ "name": "小明的家" }`
- **业务逻辑：**
  1. 自动生成 6 位字母数字 `invite_code`
  2. 创建者自动成为 `owner`（写入 `family_members`）
  3. `name` 默认为 `"{创建者昵称}的家"`

- **响应体：**
```json
{
  "id": "uuid",
  "name": "小明的家",
  "invite_code": "A3K9X2",
  "role": "owner"
}
```

---

**POST /api/v1/families/{id}/join**

加入已有家庭。

- **请求体：** `{ "invite_code": "A3K9X2" }`
- **业务逻辑：**
  1. 校验 `invite_code` 是否匹配且未过期
  2. 校验用户是否已在该家庭中（防止重复加入）
  3. 新成员默认 `role = member`，`can_manage_inventory = 0`，`can_confirm_menu = 0`
  4. 加入后通过 WebSocket 通知家庭内所有在线成员

- **错误码：** 3001=邀请码无效或已过期, 4002=已是该家庭成员

---

获取家庭成员列表。

- **响应体：**
```json
{
  "members": [
    { "user_id": "uuid", "nickname": "爸爸", "avatar_url": "...", "role": "owner", "can_manage_inventory": true, "can_confirm_menu": true, "joined_at": "..." },
    { "user_id": "uuid", "nickname": "妈妈", "role": "member", "can_manage_inventory": true, "can_confirm_menu": false, "joined_at": "..." }
  ]
}
```

---

**PUT /api/v1/families/{id}/members/{userId}/permissions**

修改成员权限（仅 owner 可操作）。

- **请求体：** `{ "can_manage_inventory": 1, "can_confirm_menu": 0 }`
- **业务逻辑：** 仅对 `role = member` 生效；`owner` 权限始终为 true，不可修改。

---

**PUT /api/v1/families/{id}/transfer-ownership**

移交掌勺权（仅 owner 可操作）。

- **请求体：** `{ "new_owner_id": "target_user_uuid" }`
- **业务逻辑：**
  1. 校验当前用户是否为 owner
  2. 校验目标用户是否为该家庭成员
  3. 当前 owner 降级为 member（保留 `can_manage_inventory = 1, can_confirm_menu = 1`）
  4. 目标成员升级为 owner
  5. 通过 WebSocket 广播掌勺人变更事件

---

**DELETE /api/v1/families/{id}**

解散家庭（仅 owner 可操作）。执行完成后家庭对所有成员不可见，所有成员自动退出。

- **业务逻辑（事务边界：单个数据库事务，全部成功或全部回滚）：**

  **Step 1 权限校验**：当前用户必须为 owner（`role = owner`），否则返回 1003

  **Step 2 软删除家庭数据（事务内按序执行）：**

  ```
  BEGIN TRANSACTION;

  (1) daily_menus: UPDATE ... SET is_deleted = 1, updated_at = now()
      WHERE family_id = ? AND is_deleted = 0
      → 获取所有 menu_id 列表

  (2) menu_items: UPDATE ... SET is_deleted = 1, updated_at = now()
      WHERE menu_id IN (上述menu_ids)

  (3) wishlist_items: UPDATE ... SET is_deleted = 1, updated_at = now()
      WHERE family_id = ? AND is_deleted = 0

  (4) inventory_batches: UPDATE ... SET is_deleted = 1, updated_at = now()
      WHERE family_id = ? AND is_deleted = 0

  (5) shopping_list_items: DELETE FROM ... WHERE family_id = ?
      (采购清单无需保留，直接物理删除)

  (6) family_members: DELETE FROM ... WHERE family_id = ?
      (成员关系直接物理删除，无需保留)

  (7) families: UPDATE ... SET is_deleted = 1, updated_at = now()
      WHERE id = ?

  COMMIT;
  ```

  **Step 3 写入 sync_queue（事务外，异步）**：将步骤 (1)-(7) 的所有软删除操作逐一写入本地 `sync_queue`，operation = 'UPDATE'（软删除）或 'DELETE'，确保其他设备能同步到删除事件。

  **Step 4 WebSocket 广播**：向所有被删除家庭成员推送 `family_dissolved` 消息，通知客户端清理本地缓存并跳转至"选择家庭"页面。

  **Step 5 清理 localStorage（客户端）**：收到 `family_dissolved` 后，客户端删除本地所有该家庭相关缓存数据。

- **错误处理**：
  - 若事务执行失败（网络中断/数据库异常），返回 5001，整个操作回滚
  - 若事务成功后 WebSocket 广播失败，不影响事务成功状态，成员下次上线时通过 delta 同步发现家庭已解散
  - 所有变更均已写入 `sync_queue`，网络恢复后可正确同步到云端

- **库存日志保留**：`inventory_logs` 不执行任何删除操作，保留完整审计记录（`family_id` 字段保留，无需归档）

- **错误码**：1003=无权限（仅 owner 可操作）

**与数据库级联删除的区别**：

| 对比维度 | 数据库 ON DELETE CASCADE | 业务层软删除（本项目） |
|---------|----------------------|-------------------|
| 删除方式 | 物理删除 | 软删除 (`is_deleted = 1`) |
| sync_queue | ❌ 无法产生记录 | ✅ 每步变更均写入队列 |
| 权限校验 | ❌ 无法控制 | ✅ 仅 owner 可执行 |
| 可逆性 | ❌ 不可恢复 | ✅ 可通过撤销解散恢复 |
| 事务边界 | 依赖数据库约束 | 显式事务控制 |

---

**接口级联与数据库级联的说明**：
数据库层面的 `ON DELETE CASCADE` **不会使用**，因为它会导致物理删除且无法写入 `sync_queue`。所有家庭数据的清理均通过业务层的软删除（步骤 (1)-(7)）实现，确保多端同步的一致性。

  1. 仅替换 `is_locked = false` 的菜品
  2. 推荐算法排除当前用户黑名单/过敏源中的菜谱
  3. 优先推荐掌勺人口味偏好匹配的菜谱
  4. 不重复推荐当前菜单中已有的菜谱

---

**POST /api/v1/daily-menus/{id}/confirm**

- **业务逻辑：**
  1. 校验当前用户是否为 owner **或** `can_confirm_menu = 1`（confirm-menu 权限与核销不同，不检查 chef_id）
  2. 设置 `is_confirmed = 1`，`confirmed_by = 当前用户`
  3. 通过 WebSocket 广播确认事件

##### 3.7 烹饪核销模块

---

**POST /api/v1/daily-menus/{id}/start-cooking**

- **业务逻辑：** 将菜单中所有 `status = pending` 的 `menu_items` 变更为 `cooking`。

---

**POST /api/v1/daily-menus/{id}/complete-cooking**

标记制作完成——触发核销流程（核心接口）。

- **请求体：**
```json
{
  "deductions": [
    {
      "ingredient_id": "uuid",
      "ingredient_name": "番茄",
      "batch_deductions": [
        { "batch_id": "uuid", "deduct_quantity": 300 },
        { "batch_id": "uuid", "deduct_quantity": 100 }
      ],
      "snapshot_recipe_amount": 400,
      "snapshot_servings": 2,
      "snapshot_recipe_name": "番茄炒蛋",
      "snapshot_ingredient_name": "番茄"
    }
  ]
}
```

- **业务逻辑（严格按序执行）：**
  1. **权限校验**：当前用户必须为 owner **或** `daily_menus.chef_id = 当前用户`（当日掌勺人），否则返回 1004
     - 核销权限与掌勺人身份严格绑定：`can_confirm_menu = 1` 的成员**不能**核销（防止非烹饪者替人核销）
  2. **快照固化**：将 `snapshot_*` 字段写入 `inventory_logs`，确保历史可追溯
  3. **FIFO 批次扣减**：按 `purchase_date ASC, expiry_date ASC` 顺序扣减批次
     - 若某批次 `batch_quantity < deduct_quantity`，则扣尽该批次后继续扣下一批次
     - 若所有批次总量不足以覆盖核销量，返回错误码 3002（库存不足），整个事务回滚
  4. **写入 inventory_logs**：每个批次的扣减生成一条 `operation = deduct, reason = cooking_deduction` 的日志
  5. **更新 menu_items**：将 `status` 变更为 `completed`
  6. **生成 consumption_records**：为每个家庭成员创建饮食消费记录（热量/营养按份数均分）
  7. **WebSocket 广播**：通知所有家庭成员库存变更和菜单完成

- **错误码：** 1004=非当日掌勺人禁止核销, 3002=库存不足

**权限模型说明**：核销必须由当日掌勺人（`chef_id`）或户主（`role = owner`）执行。`can_confirm_menu` 权限仅允许提前确认菜单（适合委托场景），不包含核销权限。

---

**GET /api/v1/daily-menus/{id}/deduction-preview**

- **业务逻辑：**
  1. 查询当前菜单中 `status = cooking` 的菜品

#### 四、WebSocket 实时同步协议

##### 4.1 连接与鉴权

- **端点**：`wss://api.example.com/ws?token=jwt_token`
- **心跳**：客户端每 30 秒发送 `{"type": "ping"}`，服务端回复 `{"type": "pong"}`。超时 60 秒无心跳则断开。
- **重连**：客户端采用指数退避重连（1s → 2s → 4s → 8s → 最大 30s）。

##### 4.2 消息格式

所有消息均为 JSON：

```json
{
  "type": "message_type",
  "payload": { ... },
  "timestamp": "2026-05-18T12:00:00Z"
}
```

##### 4.3 服务端推送消息类型

| type | 触发场景 | payload 示例 |
|------|---------|-------------|
| `inventory_changed` | 任何库存变动（入库/核销/编辑） | `{ "family_id": "uuid", "ingredient_id": "uuid", "action": "deduct", "batch_id": "uuid", "quantity_after": 200 }` |
| `menu_changed` | 菜单变更（添加/移除菜品、确认菜单） | `{ "family_id": "uuid", "menu_id": "uuid", "action": "item_added", "recipe_name": "番茄炒蛋" }` |
| `menu_completed` | 掌勺人标记制作完成 | `{ "family_id": "uuid", "menu_id": "uuid", "chef_name": "爸爸" }` |
| `chef_changed` | 掌勺人变更 | `{ "family_id": "uuid", "old_chef_id": "uuid", "new_chef_id": "uuid", "new_chef_name": "妈妈" }` |
| `wishlist_updated` | 心愿单变更 | `{ "family_id": "uuid", "action": "new_wish", "recipe_name": "红烧肉", "suggested_by": "小明" }` |
| `member_joined` | 新成员加入家庭 | `{ "family_id": "uuid", "user_id": "uuid", "nickname": "小明" }` |
| `member_left` | 成员退出家庭 | `{ "family_id": "uuid", "user_id": "uuid" }` |
| `family_dissolved` | 家庭解散 | `{ "family_id": "uuid" }` |
| `sync_conflict` | 同步冲突通知 | `{ "entity_type": "inventory_batches", "entity_id": "uuid", "server_version": 5, "your_version": 3 }` |

##### 4.4 同步承诺

- 所有推送消息必须在数据变更后 **2 秒内** 送达所有在线家庭成员
- 离线成员上线后，通过 `GET /api/v1/sync/delta?since=<last_sync_timestamp>` 拉取增量数据

bool AuthService::checkPermission(const QString &userId, const QString &familyId,
                                   const QString &permission) {
    auto member = repository_->getFamilyMember(familyId, userId);
    if (member.role == "owner") return true;
    if (permission == "manage_inventory") return member.can_manage_inventory;
    if (permission == "confirm_menu") return member.can_confirm_menu;
    return false;
}

bool AuthService::canVerifyCooking(const QString &userId, const QString &menuId) {
    auto member = repository_->getFamilyMemberByUserId(userId);
    if (member.role == "owner") return true;
    auto menu = repository_->getMenu(menuId);
    return menu.chef_id == userId;
}

#### 六、离线模式接口策略

| 场景 | 策略 |
|------|------|
| **网络正常** | Service 层调用 Repository → Repository 优先写本地 SQLite → 同时写入 `sync_queue` → Infrastructure 层异步推送到云端 |
| **网络断开** | Infrastructure 层检测到连接失败 → Repository 仅写本地 SQLite → `sync_queue` 状态保持 `pending` |
| **网络恢复** | Infrastructure 层触发重连 → 按顺序推送 `sync_queue` 中的 `pending` 项 → 成功后标记 `completed` → 冲突时触发 `sync_conflict` WebSocket 消息 |
| **首次启动** | 本地 SQLite 预置系统数据 → 连接云端后拉取家庭相关数据 → 增量同步 |

**离线降级矩阵：**

| 功能 | 离线可用 | 说明 |
|------|:--------:|------|
| 查看缓存菜谱 | ✅ | 仅本地缓存数据 |
| 查看今日菜单 | ✅ | 本地 SQLite 读取 |
| 添加/移除菜单菜品 | ✅ | 写入本地 + sync_queue |
| 查看冰箱库存 | ✅ | 本地 SQLite 读取 |
| 入库/核销 | ✅ | 写入本地 + sync_queue |
| 生成采购清单 | ✅ | 纯本地计算 |
| 创建自定义菜谱 | ✅ | 写入本地 + sync_queue |
| OCR 识别 | ❌ | 依赖第三方云端 SDK |
| 邀请家人加入 | ❌ | 需要云端生成/校验邀请码 |
| 实时同步推送 | ❌ | WebSocket 不可用 |

#### 七、接口版本与兼容性

- **URL 版本**：`/api/v1/`，重大变更时升级为 `/api/v2/`
- **向后兼容**：新增字段不影响旧客户端；删除字段需保留至少一个版本的过渡期
- **废弃标记**：响应 Header 中通过 `Sunset: <date>` 标记即将废弃的接口
