**关联设计文档：** 001.概要设计文档、004.数据库设计文档、009.开发规范文档

## 一、问题/需求描述

概要设计文档 [001:行17-40] 定义了严格的四层架构：

```
UI (QML) → Service (C++) → Repository (C++) → Infrastructure (C++/3rd)
```

每层之间有不可逾越的边界：UI 不能写 SQL，Service 不能直接 `QSqlQuery`，Repository 不知道 UI 存在。需要建立 C++ 层的抽象基类体系，让后续阶段开发有统一的接口契约。

---

## 二、思路

1. **先定契约，再写实现**：每个层次定义一个抽象基类（或模板接口），定义好虚函数签名、信号、约束注释
2. **模板 vs 虚基类的抉择**：Repository 需要操作不同类型的实体（User、Recipe、Inventory...），两条路——
   - 虚基类 + `QVariant`：统一容器但丢编译期检查
   - 模板 `BaseRepository<T>`：类型安全但 MOC 不支持
3. **常量集中管理**：主题色、营养系数、重试策略等魔法数字全部收入 `constants.h`
4. **编译即验证**：骨架写完后必须零错误零警告编译通过

---

## 三、逻辑推导

### 3.1 为什么 BaseRepository 不能用 Q_OBJECT

Qt MOC（元对象编译器）在编译前扫描头文件，为每个带 `Q_OBJECT` 的类生成 `moc_*.cpp`。模板类的元对象结构依赖于模板参数 `T`，MOC 无法在不知道 `T` 的情况下生成确定的结构，因此直接报错：

```
error: Template classes not supported by Q_OBJECT
```

**解决方案**：`BaseRepository<T>` 改为纯虚接口（不继承 `QObject`，无 `Q_OBJECT`）。派生类如 `UserRepository` 采用多重继承，`QObject` 为第一基类：

```cpp
// 纯虚接口（无 Q_OBJECT）
template <typename T>
class BaseRepository {
public:
    virtual std::optional<T> getById(const QString &uuid) = 0;
    // ...
};

// 具体实现（多重继承，QObject 必须在第一个）
class UserRepository : public QObject, public BaseRepository<User> {
    Q_OBJECT
    // 实现所有虚函数 + 自定义 signals
};
```

### 3.2 四层之间的依赖方向

```
main.cpp
  ↓ (加载 QML)
main.qml
  ↓ (QML 中 import / Connections)
Service 层 ← 持有 Repository*（依赖注入）
  ↓ (调用虚函数)
Repository 层 ← 持有 QSqlDatabase*（连接管理）
  ↓ (SQL 执行)
SQLite / PostgreSQL
```

**关键约束**：依赖箭头永远向下。上层知道下层接口，下层完全不知道上层存在。

### 3.3 乐观锁版本控制逻辑

来自 [004.数据库设计文档:行29]：每个实体有 `version` 整数字段。

并发场景推演：
```
用户A                        用户B
  │                            │
read(version=3)            read(version=3)
  │                            │
update(version=4) ──── 成功    │
  │                         update(version=4) ──── 失败 (WHERE version=3 不匹配)
```

`updateWithVersion` 返回 `false` 时，Service 层应通知用户"数据已被他人修改，请刷新"。

## 四、实施方案

### 4.1 新建文件清单

```
src/core/base_service.h        → Service 层抽象基类
src/data/base_repository.h     → Repository 模板接口
src/network/sync_manager.h     → 同步管理器桩
src/utils/constants.h          → 全局常量与枚举
```

### 4.2 BaseService 核心设计

```cpp
class BaseService : public QObject {
    Q_OBJECT
public:
    explicit BaseService(QObject *parent = nullptr) : QObject(parent) {}

signals:
    void errorOccurred(const QString &message, int errorCode);
    void operationCompleted(const QString &message);

protected:
    virtual bool verifyPermission(const QString &userId,
                                   const QString &familyId,
                                   const QString &requiredRole);
};

// 默认实现：基类放行，派生类覆写
inline bool BaseService::verifyPermission(...) { return true; }
```

### 4.3 BaseRepository 核心设计

```cpp
template <typename T>
class BaseRepository {
public:
    virtual ~BaseRepository() = default;
    virtual std::optional<T> getById(const QString &uuid) = 0;
    virtual QList<T> getAll() = 0;
    virtual bool save(const T &entity) = 0;
    virtual bool update(const T &entity) = 0;
    virtual bool softDelete(const QString &uuid) = 0;
    virtual bool updateWithVersion(const T &entity, int expectedVersion) = 0;
};
```

### 4.5 编译过程中修复的 3 个坑

| # | 问题 | 根因 | 修复 |
|---|------|------|------|
| 1 | `Template classes not supported by Q_OBJECT` | MOC 无法处理模板类的元对象 | 改为纯虚接口 |
| 2 | `Qt requires a C++17 compiler` + `/permissive-` | MSVC 默认不开启标准合规模式 | 加 `/Zc:__cplusplus /permissive- /utf-8` |
| 3 | 找到的是 `mingw_64` Qt 但编译器是 MSVC | Qt 安装包含多版本，CMake 默认选错 | `CMAKE_PREFIX_PATH` 固化 `msvc2022_64` |

## 五、可行性分析

| 维度 | 评估 |
|------|------|
| **扩展性** | 新增实体只需写一个 `XxxRepository : QObject, BaseRepository<Xxx>`，不需要改接口 |
| **编译安全** | 纯虚接口 + concrete 多重继承，编译期即可发现缺少实现 |
| **Qt 兼容** | `QObject` 多重继承规则（第一个基类必须是 `QObject`）已验证可行 |
| **单人维护** | 4 个头文件总计约 200 行，核心契约一目了然 |
